  height.E ~ noise(0.2)               # depends on: nothing (random)

  - Parse formula → build DAG → toposort → execute in order
  - Each node writes its result into PhenotypeArray
  - Simple, predictable, easy to debug

  - Nodes are computed on demand when referenced

  Now let me critique this against the current codebase realities.

  Critique

  1. Effect standardization is under-specified

  The current system has a confusing matrix of beta_raw_diploid,
  beta_scaled_standardized_haploid, etc. (4+ variants). The new design says
  standardized: bool but doesn't address when standardization happens.

  When computing haplotypes.matvec(effects), does the operator standardize
  internally, or does the caller pass pre-transformed effects? If the operator
  standardizes, it needs allele frequencies. If the caller transforms, every
  architecture node needs to know the convention.

  Recommendation: Standardization should live in EffectSpec, not the operator.
  EffectSpec.get_effects(af) returns the correctly-scaled vector for raw
  genotype matvec. The operator always does raw G @ beta. This keeps the
  operator simple and effect logic contained.

  2. PhenotypeArray namespace collisions

  Using dot-separated strings (height.G, height.E, height) means the system
  needs to parse strings to answer "what are the components of height?" This is
  fragile.

  Recommendation: Keep the flat dict, but add a method components_of(phenotype) 
  -> dict that does prefix matching. Or track the phenotype→component mapping
  explicitly in the Architecture at parse time.

  3. Missing: how mating accesses phenotypes

  Currently, LinearAssortativeMatingRegime takes a ComponentIndex to know which
  phenotype columns to sort on. With PhenotypeArray as a dict of strings, the
  mating regime needs phenotype names.

  Recommendation: Mating regime constructor takes phenotypes: list[str] and
  weights: list[float]. It indexes into PhenotypeArray by string name. Simple.

  4. Missing: offspring SampleMeta creation

  Who creates the offspring SampleMeta (new iids, fids, sex assignment)?
  Currently this happens in MateAssignment. The new system needs the same —
  mating produces a MateAssignment with offspring metadata, then
  HaplotypeOperator.meiosis() uses it.

  Recommendation: Keep this in the mating regime. MateAssignment contains
  offspring SampleMeta + parent indices.

  5. Missing: filtering

  The current system has filters.py with sample filtering between mating and
  statistics. The new design doesn't mention filtering.

  Recommendation: Filtering is just boolean indexing on HaplotypeOperator and
  PhenotypeArray. No special system needed — users can do haplotypes[mask, :]
  directly. If you want automatic per-generation filtering, it's a hook in the
  simulation loop.

  6. | FID grouping — who resolves the group?

  height.famEnv ~ cnoise(0.1) | FID needs to:
  1. Look up FID in SampleMeta (core field or extra)
  2. Draw one value per unique FID
  3. Broadcast to all samples sharing that FID

  This means architecture execution nodes need access to SampleMeta, not just
  haplotypes. The compute() signature needs to pass it (it's on
  haplotype_history[gen].samples, so it's available, but the execution engine
  needs to thread it through).

  7. Sibling references — who are siblings?

  sibling_mean(X) needs sibling identity. Is this FID-based (all individuals
  sharing FID in the same generation)? Or pedigree-based (share at least one
  parent)? For the current mating model where each pair produces multiple
  offspring, these are equivalent. But with complex pedigrees (half-siblings),
  they diverge.

  Recommendation: Define siblings as same-FID-same-generation. Simple, covers
  the common case. Document the assumption.

  8. Multivariate node execution

  (height.G, bmi.G) ~ mvEffects(eff) is one node in the DAG but produces two
  outputs. The toposort needs to handle multi-output nodes — downstream nodes
  referencing height.G or bmi.G should depend on this single node.

  Recommendation: The execution plan should have a concept of "node outputs" vs
  "node identity." A single mvEffects node registers both height.G and bmi.G as
  outputs. The dependency graph tracks output names, but execution fires the
  node once.

  9. Post-processors may still be useful

  With configurable retention replacing LimitMemory, do we need post-processors
  at all? The current system uses them for custom per-generation hooks (e.g.,
  saving snapshots, logging).

  Recommendation: Keep a simple callbacks: list[Callable] on Simulation instead
  of a formal PostProcessor class. Lighter weight.

  10. What about the current .xft compatibility shim?

  The ajay branch already has NHaplotypeArrayAccessor providing .xft-like
  access. In the ground-up rewrite, do we keep any backwards compatibility?

  Recommendation: No. Clean break. The new API is different enough that a shim
  would be confusing. Old code uses the old package; new code uses the new API.

  ---
  Overall assessment: The design is solid. The biggest gaps are (1) effect
  standardization mechanics, (2) explicit specification of how data flows into
  execution nodes (SampleMeta, pedigree), and (3) a few "who creates what"
  questions around offspring metadata. None of these are architectural blockers
  — they're implementation details to nail down in Phase 1-2.

  What are your thoughts on these critiques? Anything you disagree with or want
  to discuss further?
