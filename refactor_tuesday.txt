● You're right - sibling effects are substantially more complex than parent
  effects. Let me think through the challenges:

  Why sibling effects are hard:
  Challenge: Direction
  Parent effects: Cross-generational (clear)
  Sibling effects: Within-generation (ambiguous)
  ────────────────────────────────────────
  Challenge: Count
  Parent effects: Always 2 parents
  Sibling effects: Variable (0 to many siblings)
  ────────────────────────────────────────
  Challenge: Causality
  Parent effects: Parent → child (clear)
  Sibling effects: Sibling ↔ sibling (potentially cyclic)
  ────────────────────────────────────────
  Challenge: Timing
  Parent effects: Parents computed first
  Sibling effects: Siblings computed simultaneously?
  Key design questions:

  1. How to reference siblings?
  # Average across all siblings
  edu.sib ~ sibling_mean(edu)

  # Any sibling with condition
  health.sib ~ sibling_any(disease)

  # Count of siblings with trait
  risk.sib ~ sibling_count(smoker)

  # Weighted by birth order?
  outcome.sib ~ sibling_weighted(outcome, weights='birth_order')

  2. How to handle cycles?

  If Alice's edu depends on Bob's edu, and Bob's edu depends on Alice's edu, you
   have a cycle.

  Options:
  - A: Only allow sibling effects on components, not phenotypes - sibling's G
  affects my outcome, not sibling's final phenotype
  - B: Birth order breaks ties - older siblings computed first
  - C: Equilibrium computation - iterate until convergence
  - D: Lag - use sibling values from previous "time step" (within-generation
  iteration)

  3. What about sibling shared genetics?

  Siblings share ~50% of haplotypes. You might want:
  # Genetic material shared with sibling (IBD)
  height.sib_G ~ sibling_shared_genetic(effects)

  This requires tracking IBD segments, which is a different data structure
  challenge.
